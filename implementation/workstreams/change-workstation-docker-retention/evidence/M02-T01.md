## Supported bounded-GC controls

The installed `docker buildx prune --help` supports:
- `--builder string`;
- `--filter filter`;
- `--max-used-space bytes`;
- `--min-free-space bytes`;
- `--reserved-space bytes`;
- `--all`;
- `--force`.

Docker's Buildx documentation confirms that prune clears cache for the selected builder and that `max-used-space` applies an LRU-style upper bound. It also documents filters such as `until`, `description`, `type`, `shared`, and `private`.

Installed `docker buildx create --help` lists manually creatable drivers `docker-container`, `kubernetes`, and `remote`; it does not offer a second manually-created `docker` driver. Docker documents the default `docker` driver as the BuildKit instance built into Docker Engine and not manually creatable, while `docker-container` creates a dedicated BuildKit container with persistent cache in a dedicated Docker volume.

## Scope conclusion

Pruning the current `default` builder is not an acceptable workstation-only retention mechanism:
- it is the daemon's shared `docker` driver;
- its cache inventory is not a Workstation-owned namespace;
- content/description filters are properties of individual cache records, not a durable project ownership boundary;
- a global/default-builder size policy could therefore evict cache belonging to unrelated Unraid builds.

The safe implementation path is to give Workstation its own named `docker-container` Buildx builder and always select it explicitly for Workstation builds. Cache GC can then target that exact builder with `docker buildx prune --builder <workstation-builder> ...`, making builder identity the ownership boundary.

A concrete bounded policy may use the installed size controls on that dedicated builder. Execution Prep may select the exact finite `max-used-space` / `reserved-space` defaults and must keep them configurable. The implementation should include `--all` if the accepted bound is intended to cover frontend/internal cache as well as ordinary records.
