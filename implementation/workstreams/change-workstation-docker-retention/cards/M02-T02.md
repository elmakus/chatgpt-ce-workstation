### Must preserve

- Workstation builds must stop using the daemon-global `default/docker` builder cache as their ownership boundary.
- Use a dedicated named Buildx builder with driver `docker-container`; default name: `chatgpt-ce-workstation`.
- Select the dedicated builder explicitly for Workstation builds; do not change the operator's global/current Buildx builder selection.
- If an existing builder with the configured Workstation name is not a `docker-container` builder, fail closed before building rather than reusing or replacing it.
- Keep identity-driven BuildKit cache reuse enabled; no `--no-cache` or timestamp invalidation.
- Cache cleanup is allowed only after the exact promoted candidate has passed health and runtime verification.
- Cache cleanup must target the exact dedicated builder and must never call an unscoped `docker builder prune`, `docker buildx prune` without `--builder`, or `docker system prune`.
- Use a finite size bound on the dedicated builder cache. Defaults are `max-used-space=24gb` and `reserved-space=8gb`; both may be explicit non-secret operator overrides.
- The bound must cover internal/frontend cache too, so the scoped prune uses `--all`.
- A post-success cache cleanup failure is a retention warning, not a production rollback/update failure.
- Persist non-secret build-cache policy/result evidence separately from image cleanup evidence.
- Do not delete or alter persistent home/projects/secrets/keyring data.
- Do not clean historical cache from the shared `default/docker` builder because M02-T01 could not prove Workstation-only ownership of those records.

### Must not / rationale that must travel

- Do not use content-description matching as the ownership boundary; M02-T01 established that cache record descriptions are not a durable project namespace.
- Do not use or switch the global current builder with `docker buildx use`.
- Do not remove/recreate an existing conflicting builder automatically.
- Do not run any real builder creation, build, prune, image deletion, production recreate, or updater invocation on Tower in this Card. The explicit live-write gate remains M04.

## Outcome

Source and deterministic tests make every future Workstation build use its own persistent BuildKit cache namespace and perform builder-scoped bounded cache GC only after verified production success.

## Scope

- Wire `scripts/build.sh` to ensure/select the dedicated builder explicitly.

- Add non-secret configuration defaults/overrides for builder name and size bounds.
- Extend durable update evidence with builder identity, policy values and cache-cleanup status.
- Add deterministic tests for builder creation/validation, explicit build selection, exact prune scoping/limits, success ordering and cleanup-warning semantics.

## Acceptance

- With no pre-existing dedicated builder, the source path creates exactly the configured named `docker-container` builder and never marks it globally current.
- With a matching existing builder, it is reused.
- With a conflicting driver under the same name, the build fails closed before the candidate build.
- `docker compose build` is invoked with the exact configured builder while retaining BuildKit cache semantics.
- Post-success cache GC invokes only `docker buildx prune --builder <exact-name> --all --max-used-space 24gb --reserved-space 8gb --force` by default, or exact explicit configured limits.
- Cache GC is absent on all pre-promotion, promotion, health/runtime failure and rollback paths.
- Cache GC failure after production verification leaves update status successful while retention evidence reports a warning.
- Durable evidence records builder name, driver contract, max/reserved-space policy and cleanup status without secrets.
- No global/default-builder prune or global `buildx use` path exists.
- Existing M01 image retention, rollback and success semantics remain GREEN.
