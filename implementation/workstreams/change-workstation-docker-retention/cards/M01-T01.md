# M01-T01 — Implement reference-safe post-success image retention

- Milestone: `M01`

> This file is a stable Task Card contract. Mutable execution/review/result state lives only in the selected manifest-bound workstream Task Board.

### Must preserve

- Retention cleanup is unreachable until the exact promoted candidate has passed both health and runtime verification.
- Every pre-promotion or post-promotion verification failure retains the exact previous known-working image and follows the existing deterministic rollback path.
- The protected image set after success is the exact current verified production image plus exactly one immediately previous known-working rollback image.
- Cleanup decisions are identity/reference driven, not age-only.
- Cleanup is restricted to workstation-owned `candidate-*` / `rollback-*` references in the candidate repository and must not use any global/unscoped prune.
- A protected identity must remain safe even when several workstation tags point to it.
- An image object must not be force-removed through another live Docker reference; stale workstation tags may be removed without overriding Docker reference safety.
- Persistent bind-mounted home/projects/secrets/keyring data remain completely outside this Card.
- Cleanup failure after verified production success is non-fatal for the update and must be surfaced separately in durable evidence/output.
- Existing identity-driven build-cache behavior is unchanged; BuildKit cache retention belongs to M02.

### Must not / rationale that must travel

- Do not add `docker system prune`, unscoped `docker image prune`, global builder prune, or force-delete semantics.
- Do not implement BuildKit cache GC in this Card.
- Do not move cleanup earlier than the R12 success boundary to simplify control flow.
- Do not classify post-success cleanup failure as an update failure or invoke rollback because cleanup failed.

## Dependencies

- none beyond approved `workstation-docker-retention-R1`

## Outcome

The updater performs reference-safe workstation image/tag retention only after verified promotion, retains the exact current production image plus the immediately previous known-working rollback image, removes only stale workstation-owned references when safe, and records cleanup status without weakening rollback behavior.

## Scope

### Included

- Add bounded helper(s) in `scripts/update.sh` for workstation-owned candidate/rollback reference discovery and reference-safe cleanup.
- Invoke image retention only after candidate health/runtime verification is GREEN.
- Protect current and previous image identities and their required references.
- Remove stale workstation-owned candidate/rollback tags and remove image objects only when ordinary Docker reference semantics permit it.
- Extend successful update evidence/output with protected current/rollback identities and image-cleanup result at a bounded level.
- Make image-retention failure a post-success warning/result rather than a production update failure.
- Extend deterministic shell/orchestration tests for cleanup ordering, protected identities, reference safety and cleanup-failure behavior.

### Excluded

- BuildKit/build-cache retention policy or commands (M02).
- Full three-cycle integrated retention harness beyond what is directly required to validate M01 helpers (M03 owns the required multi-cycle proof).
- Live Unraid Docker mutation or deployment (M04 explicit authorization gate).
- Unrelated updater/keyring/refactoring changes.

## Acceptance

- No retention helper runs on source, resolver, preflight, build, candidate-readback, promotion, promoted-image-mismatch, health or runtime-verification failures.
- On success, the exact candidate image identity and exact previous image identity are protected.
- Exactly one immediately previous known-working rollback reference remains the normal rollback baseline; older workstation candidate/rollback references are eligible for removal only after the new candidate is verified.
- Multiple workstation tags that resolve to either protected image remain safe.
- A stale workstation tag can be removed without forcing deletion of an image that still has another live Docker reference.
- No global/unscoped prune or force-delete command is introduced.
- Successful production verification remains success when image retention reports a cleanup failure; rollback is not invoked for that cleanup failure.
- Durable success evidence identifies protected current/rollback identities and a bounded image-cleanup result without secrets.
- Existing updater rollback and source/orchestration tests remain GREEN.
