## Findings

### F1 — helper success does not relock in the candidate lifecycle

A disposable probe using exact failed candidate image `sha256:c4f4028d846048bc13157913a9e21ef0ccac0929f54bc3f41109e40aeb502c1c` and a production-derived keyring copy kept the canonical login collection unlocked after helper success across delayed checks through 5 seconds.

A second disposable full-container probe using the same candidate image and a copy of the current live persistent keyring state likewise reached the session-readiness boundary with `login == default`, and the canonical collection remained `Locked=false` across delayed checks. The current production keyring files were copied only into disposable local state; live persistent keyring bytes were not mutated.

This disproves the working hypothesis that helper process exit or normal post-helper daemon lifecycle immediately relocks an otherwise-correct migrated collection.

### F2 — strict verifier has an output-format false negative

The exact reviewed verifier uses:

`gdbus call ... org.freedesktop.DBus.Properties.Get org.freedesktop.Secret.Collection Locked | grep -F 'boolean false'`.

On Tower, a read-only query of an actually unlocked canonical login collection returns from `gdbus`:

`(<false>,)`

and the verifier's literal `grep -F 'boolean false'` returns status 1.

The same property queried through `dbus-send --print-reply ... org.freedesktop.DBus.Properties.Get string:org.freedesktop.Secret.Collection string:Locked` returns:

`variant       boolean false`.

The candidate disposable probes also report `gdbus` Locked output as `(<false>,)` while the collection is demonstrably unlocked. Therefore the two live retry failures labeled `canonical login Secret Service collection is locked` are consistent with a verifier parser mismatch rather than a proven runtime relock.

### F3 — smallest bounded correction

Keep strict candidate verification semantically unchanged, but query the Locked property with the already-required `dbus-send` tool (or equivalently parse the actual `gdbus` variant representation exactly). The minimal correction is to replace only the Locked-property `gdbus` pipeline with `dbus-send --print-reply` and retain the existing requirement that the returned boolean be false.

Add a deterministic regression that exercises the lock-check contract against representative D-Bus replies so an unlocked `boolean false` reply passes and a locked `boolean true` reply fails. Source validation must include that regression.

No change to D26, R11/R12, migration semantics, readiness semantics, rollback semantics, or issue #11 is required.
