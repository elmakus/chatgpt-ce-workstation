## Known evidence

## Questions

1. Can an encrypted login collection be already unlocked when `keyring-passwordless.py` starts, causing the helper to skip `ChangeWithMasterPassword` and incorrectly write its marker?
2. What observable operation safely proves that the persistent collection is passwordless across daemon/session restart without deleting items?
3. Does the real keyring contain alias/state/layout details not represented by the synthetic fixture?
4. What rollback verifier contract can validate exact restoration of an older retained image without applying candidate-only invariants, while keeping strict candidate verification unchanged?
5. What rollback state cleanup must occur even when no migration backup directory was created?

## Findings

### F1 — production legacy keyring was not readable by the candidate desktop user

Read-only Tower inspection established that the persistent legacy file:

`/mnt/user/appdata/chatgpt-ce-workstation/home/.local/share/keyrings/login.keyring`

is `uid=0 gid=0 mode=0600` and its file header reports four items. The supervised desktop/keyring process runs as `codex` (UID 99) through `s6-setuidgid codex`, so that file is not readable by the intended Secret Service process.

This is consistent with the previously documented pre-MF-T01 root-owned secondary keyring daemons that inherited `HOME=/home/codex` and could mutate persistent keyring state as root.

### F2 — the failed candidate created a replacement/split collection instead of migrating the four-item legacy keyring

Three UID-99 files were created/modified in the exact failed-candidate window:

- `Login.keyring`;
- `default`, whose content is the non-secret alias name `Login`;
- `login_1.keyring`.

Current read-only Secret Service introspection on the restored old image shows:

- `default -> /org/freedesktop/secrets/collection/Login`;
- `login -> /org/freedesktop/secrets/collection/login`;
- the visible `login` collection has zero items;
- the visible `Login` collection has one item;
- that one item's non-secret label is `Chromium Safe Storage`, created during the failed-candidate window.

The legacy binary `login.keyring` still reports four items on disk, but those items are not visible through the current codex Secret Service. This proves a split-brain state: the candidate created/used a replacement collection while the original four-item keyring remained stranded behind incorrect ownership.

### F3 — current helper semantics permit false completion

Current `keyring-passwordless.py`:

- reads `default` before `login`;
- creates a new passwordless collection when the selected aliases are unavailable;
- sets only the `default` alias on creation;
- creates a backup only in the branch where the selected collection is locked and a legacy password is needed;
- writes the durable v1 marker after the selected collection is merely observed unlocked.

Therefore a replacement collection can become unlocked and receive the marker without the original login keyring ever being backed up or migrated.

The exact-byte disposable-copy command was not executed because the remote execution safeguard blocked that mutation-oriented probe. No attempt was made to bypass the safeguard. Direct live metadata + process ownership + exact candidate-created file timestamps + D-Bus introspection are sufficient to establish the production failure mechanism; the correction Card must still add a deterministic regression fixture modeling an unreadable/root-owned legacy login keyring.

### F4 — migration preparation must be root-owned and rollback-safe

The root init phase runs before the desktop service and can read the root-owned legacy keyring. The smallest safe correction is:

1. use a new migration generation (`passwordless-v2`) so stale v1 success state cannot suppress the correction;
2. before changing ownership/content, create one root-side backup of the whole keyring directory when v2 is pending;
3. repair keyring-directory ownership to the codex UID/GID so the canonical desktop daemon can see the legacy file;
4. preserve all additional collections/files produced by the failed v1 attempt rather than deleting them;
5. migrate the canonical login collection with the retained legacy credential when present, regardless of its transient Locked property;
6. set both `login` and `default` aliases to the successfully migrated canonical collection;
7. write the v2 marker only after migration/verification succeeds.

GNOME Initial Setup uses the same internal `ChangeWithMasterPassword` interface with explicit old/new secrets to change the login keyring password, supporting this direct old->empty migration model.

### F5 — rollback state cleanup must not depend on backup existence

Current `restore_keyring_migration_backup()` removes the marker only inside the backup-present branch. A candidate that wrote a marker without creating a backup therefore leaves stale completion state after rollback.

Rollback must clear candidate-era v1/v2 completion markers unconditionally. When a v2 backup exists, restore it before starting the previous image.

### F6 — rollback verification must be backward-compatible, candidate verification must remain strict

The exact previous image `ea264b43...` was restored, running and healthy, but current-source `verify-runtime.sh` rejected it because it predates the new fail-closed D-Bus invariant.

R11 requires verified deterministic rollback; it does not require applying candidate-only runtime invariants to an older known-working image.

The bounded correction is a distinct rollback-baseline verifier that checks version-stable safety/readback only:

- exact expected image ID;
- container running + healthy;
- restart policy;
- exact persistent home/project binds;
- absence of Docker socket/host-root mount;
- unprivileged/no `SYS_ADMIN`.

The strict current `verify-runtime.sh` remains unchanged in purpose and continues to gate the promoted candidate, including D26 marker/alias/keyring/session checks.
