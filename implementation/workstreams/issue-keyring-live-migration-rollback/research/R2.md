## User-run Tower evidence — 2026-09-20

The locally executed disposable-copy harness satisfied the previously blocked evidence path without mutating live production state. It established a production-derived copy with a canonical legacy login collection containing 4 items and reproduced the pre-fix failure class: the old helper returned success while the resulting alias/canonical state was not the required preserved login state.

The corrected reviewed subject `35d1b9dd91287c2953c56824f91716a77c59afd7` then exposed an implementation defect against a fresh production-derived copy. Password migration itself reached the 4-item canonical login collection and unlocked it, but the helper failed with:

`org.freedesktop.DBus.Error.NotSupported: Only the 'default' alias is supported`

The failure occurs at `SetAlias("login", collection)`. This GNOME Secret Service implementation supports writing only the `default` alias. An isolated empty-home probe additionally proved that creating a collection with label `login` (lowercase) materializes the natural `login` alias and makes both `login` and `default` resolve to that collection, whereas label `Login` creates `Login.keyring` and leaves `login` unresolved.

Classification evidence: this is an L1/L2 implementation defect inside the accepted Card authority, not a requirement/Definition change. The Card requirement that both aliases converge remains valid; the implementation must achieve it using GNOME's natural `login` collection semantics plus the writable `default` alias instead of attempting to write the reserved `login` alias.

No live updater/promotion was run. The production container remained on the known-working rollback image during the evidence run.
