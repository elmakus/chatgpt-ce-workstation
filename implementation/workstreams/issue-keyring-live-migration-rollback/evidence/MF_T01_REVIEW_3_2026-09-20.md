## Blocking finding

### R1 — interrupted first backup can become a permanently trusted partial rollback snapshot

MF-T01 acceptance requires the **whole** persistent keyring directory to be backed up before ownership/content mutation, with rollback able to restore exact pre-attempt state.

On the reviewed subject, `prepare_keyring_passwordless_v2` performs:

```bash
if [[ ! -e "$backup" ]]; then
  cp -a -- "$keyring_dir" "$backup"
fi

chown -R "$target_uid:$target_gid" "$keyring_dir"
```

`cp -a` creates/populates the destination incrementally. If that first copy is interrupted or fails after creating `$backup` but before copying the whole directory, the failed invocation correctly stops before `chown`, but the partial backup directory remains.

On the next container start, `[[ -e "$backup" ]]` is true, so the code skips copying and treats the partial directory as the preserved pre-attempt backup, then mutates active ownership. A later rollback removes the active keyring directory and moves that incomplete backup into place. Missing keyring files/items can therefore be lost precisely on the recovery path intended to preserve them.

The helper-side `backup_keyrings()` has the same existence-only trust rule, so it does not repair this state.

This violates:
- MF-T01 Acceptance 1: whole-directory backup before ownership/content mutation;
- MF-T01 Must preserve: every existing keyring collection/item;
- D26 in-place migration without deleting stored items;
- R11 deterministic rollback protection.
