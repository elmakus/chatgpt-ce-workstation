## Verified evidence

### Exact installed Codex release

The installed client reports `codex-cli 0.155.0-alpha.9.2`.

Upstream tag `rust-v0.155.0-alpha.9.2` resolves to commit `4607249e430dac1c961df4dc615beae88e33cec8`.

At that exact commit, `codex-rs/core/tests/suite/websocket_fallback.rs` contains `websocket_fallback_switches_to_http_on_upgrade_required_connect`. The test configures a Responses provider with WebSocket support, makes GET `/responses` return HTTP 426, and requires the first real turn to continue through HTTP POST `/responses`. The test explicitly documents 426 as an immediate switch-to-HTTP condition.

The same exact release exposes `supports_websockets` as a provider capability and its built-in OpenAI provider enables it. WebSocket fallback is session-scoped/sticky once activated.

### Exact codex-chatgpt-web release

Reviewed/published Workstation dependency `elmakus/codex-chatgpt-web@d7c9db70cf1d54029c061490d73335146a23ed28` intentionally implements:
- GET `/v1/responses` → HTTP 426 with message that Responses WebSocket transport is not enabled on the local route;
- POST `/v1/responses` → the normal HTTP Responses handler.

Therefore the bridge's 426 behavior is intentionally aligned with the exact installed Codex fallback contract; adding WebSocket support to the bridge is not required by this evidence.

### Live target-host verification

After the original M01-T18 rollback, production remained on exact image `sha256:9ede8f1f522a710707acac32d01fd8c4d7671b91912791e299d1c635d964b893`, healthy, with Muse unset.

The earlier blocker classification came from treating the prewarm/connect diagnostic line as terminal before observing the full turn lifecycle.
