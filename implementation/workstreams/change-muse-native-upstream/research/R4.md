## Finding

The M01-T18 failure is a third independently evidenced Muse/Meta tool-schema compatibility boundary. The accepted Project Definition remains sufficient, but approved plan R8 is no longer sufficient because it authorizes only the Gmail omission plus the `web_search.search_content_types` normalization and explicitly expects every other Muse tool/property to pass unchanged.

The correct final owner is Strategic Planning for a material R9 execution-strategy revision. No Project Definition change is required.

## Verified evidence

### 1. Real Codex Desktop reproduces the exact Meta rejection

A real user-facing Codex Desktop turn using `Muse Spark 1.3 Contributor` fails before tool execution with:

`Recursive JSON schemas are not currently supported`

The structured provider error identifies `param: parameters` and `type: invalid_request_error`.

This is stronger root-cause evidence than the earlier manual app-server timeout. It demonstrates provider-side validation of a tool/function parameter schema.

### 2. The problem is a known current Codex Desktop + Meta/Muse incompatibility

Open issue `openai/codex#44144` reports the same failure for Codex Desktop with `muse-spark-1.3-contributor`. The reporter verifies the same Codex binary/config succeeds through CLI while Desktop fails, and narrows the delta by elimination to Desktop-injected `codex_app` task tools plus Desktop-managed `node_repl`.

As of this research:
- the issue remains open;
- it has no maintainer comments;
- no matching upstream Codex provider-normalization fix or PR was found.

The exact failing Desktop tool cannot be re-inspected on the target host while Tower is offline, so R4 does **not** claim one specific tool name as the sole culprit. The product-level compatibility rule must cover verified local recursive schemas without depending on a single current Desktop tool name.

### 3. Independent reports prove Meta/Muse rejects recursive tool schemas as a general class

Relevant OpenCode reports independently reproduce the same Meta error from different recursive tool sources:
- `anomalyco/opencode#45800`: PostgreSQL MCP with a self-recursive `$defs.__schema0` reached through array `items` / object `additionalProperties`;
- `anomalyco/opencode#45823`: houseCARL MCP recursive refs;
- `anomalyco/opencode#47157`: Synara-added tools with Muse 1.3;
- `anomalyco/opencode#48151`: specifically Codex Desktop + Muse 1.3, linked to `openai/codex#44144`.

Therefore the compatibility boundary is not Gmail-specific and is not safely modeled as a list of one or two known tool names.

### 4. Exact installed Codex intentionally preserves local refs/definitions

Installed Codex is `0.155.0-alpha.9.2`; upstream tag `rust-v0.155.0-alpha.9.2` resolves to commit `4607249e430dac1c961df4dc615beae88e33cec8`.

At that exact commit, `codex-rs/tools/src/json_schema.rs` explicitly preserves `$ref` and reachable local `$defs` / `definitions` while lowering tool schemas. It also follows local refs when pruning unreachable definitions.

Thus the recursive local refs reaching Muse are not accidental byte noise that can be deleted indiscriminately. Ordinary Responses-compatible providers intentionally receive them and ordinary-native behavior must remain unchanged.

### 5. Existing fork boundary remains the smallest deterministic correction point

Released fork subject `elmakus/codex-chatgpt-web@d7c9db70cf1d54029c061490d73335146a23ed28` already owns the two proven Muse-only request normalizations in `src/native-passthrough.ts`:
- exact Gmail namespace omission;
- exact `web_search.search_content_types` property omission.

The normalization runs only for `responses` requests whose validated model is `muse-*`, then reserializes the body and clears stale content encoding only when a rewrite occurs. Ordinary native requests remain byte-preserved when no bridge-owned rewrite applies.

Adding the recursive-schema compatibility at this same Muse-only decoded-body boundary avoids changing Workstation routing, CLIProxyAPI production, or ordinary native behavior.

### 6. Evidence favors bounded local-ref inlining with cycle-only widening, not dropping tools

Two OpenCode correction attempts provide useful implementation evidence:

- PR `#29295` proposes recursively inlining local `#/...` refs, preserving non-recursive schema structure and `$ref` siblings, removing definition tables after expansion, and replacing only a recursive re-entry with permissive `{}`. Its regression example preserves the recursive object's normal properties while only the cycle edge becomes `{}`.
- PR `#16910` proposes the coarser fallback of replacing an entire circular input schema with `{type:"object", additionalProperties:true}`.

Neither PR is merged upstream, so neither is authority by itself. However, the first algorithm is materially narrower and better matches this project's requirement to keep non-Gmail tools available unless the verified provider constraint forces a capability reduction.

The planning contract should therefore prefer:
- local fragment refs only (`#/$defs/...`, `#/definitions/...`, and other resolvable local JSON Pointer forms);
- inline resolvable non-recursive refs;
- use an active-reference stack and replace only the recursive re-entry with a permissive schema node;
- preserve ref siblings and all non-recursive shape;
- remove now-unneeded local definition tables after successful inlining;
- do not silently widen unresolved/non-local refs;
- do not remove the entire tool merely because one schema edge is recursive.

Exact helper structure remains L1 implementation detail; the behavioral acceptance above is the durable requirement for execution.

### 7. Existing Definition authority is sufficient

Approved Requirement R7 and Decision D30 already state that non-Gmail Muse tools remain untouched **unless separate verified incompatibility evidence establishes another exception**.

R4 supplies that evidence. The required correction:
- keeps every affected tool present;
- changes only provider-unsupported recursive schema representation on Muse-bound Responses requests;
- leaves ordinary native/Codex-LB schemas unchanged;
- leaves browser-backed `chatgpt-web/*` unchanged;
- keeps request-body/provider compatibility in the existing fork boundary;
- requires no CLIProxyAPI production mutation.

No accepted product/system intent, routing decision, secret boundary, or authorization boundary changes.

### 8. R8 execution strategy is insufficient and must be revised

R8 explicitly describes a final Muse turn succeeding under **two** verified normalizations and requires every other Muse property to remain unchanged. Continuing implementation under that wording would exceed the approved execution strategy.

R9 must preserve all completed R8 evidence but add:
1. immediate restoration of the Muse-disabled baseline as the first target-host operation when Tower returns online;
2. a third bounded Muse-only local-recursion schema normalization in the related fork;
3. focused independent review/release provenance for that correction;
4. D25 consumption of the next exact release;
5. reactivation only after the corrected release is promoted;
6. final acceptance through a **real Codex Desktop** Muse turn with the Desktop-only tool surface, not a toy helper that can silently fall back to the default model;
7. ordinary-native recursive-schema preservation and browser-backed controls;
8. secret-safe proof that recursive local refs no longer reach Muse while non-recursive schema/tool structure remains.
