## Verified findings

### 1. The failure is one property on the Codex `web_search` tool, not the web-search tool itself

The production M01-T13 normal-client probe failed with Meta's exact validation error:

`tools[].search_content_types is only supported for web_search_preview tools.`

A direct, secret-safe differential probe through the same operator-managed CLIProxyAPI v7.3.4 / Meta Muse route isolated the field:

- `{"type":"web_search","search_content_types":["text","image"]}` -> HTTP 400 with the same `invalid_request_error` and exact parameter `tools[].search_content_types`;
- `{"type":"web_search"}` with the field omitted -> HTTP 200 and a normal Responses object.

Therefore the current Muse provider supports the `web_search` tool itself but rejects the multimodal `search_content_types` extension on that tool shape. Removing the complete web-search tool is neither necessary nor justified by the evidence.

### 2. Current OpenAI Codex already models this as a provider-specific web-search capability

Current upstream `openai/codex` source at commit `3483294596ea86edd1fdc30bf360b8951b9d7022` defines `WebSearchToolType::{Text, TextAndImage}`. `create_web_search_tool` emits `search_content_types: ["text", "image"]` only for `TextAndImage`; `Text` omits the field.

Primary source:
- `codex-rs/protocol/src/openai_models.rs`
- `codex-rs/core/src/tools/hosted_spec.rs`

The same upstream has an explicit provider normalization for Amazon Bedrock with the comment that Bedrock rejects `search_content_types`; it sets `model.web_search_tool_type = WebSearchToolType::Text` rather than disabling web search.

Primary source:
- `codex-rs/model-provider/src/amazon_bedrock/catalog.rs`

This is strong upstream prior art for preserving web search while suppressing only a provider-unsupported multimodal field.

### 3. CLIProxyAPI v7.3.4 forwards the translated Codex Responses body to Meta without stripping this property

The running container is `eceasy/cli-proxy-api:v7.3.4`. Upstream tag `router-for-me/CLIProxyAPI@v7.3.4` resolves to commit `8335eac731946bd4eff18f500653f93736df53d6`.

At that tag, `internal/runtime/executor/meta_executor_execute.go` translates the incoming request to Codex Responses shape, applies general request config/sanitization, and posts the resulting body to `<meta-base>/responses`; it has no Meta-specific `search_content_types` normalization.

The tag's Codex Responses translator normalizes legacy `web_search_preview*` aliases to `web_search` but does not remove `search_content_types` from the resulting tool object:
- `internal/translator/codex/openai/responses/codex_openai-responses_request.go`

This makes the observed 400 an upstream/provider compatibility boundary, not a Workstation routing defect.

### 4. The existing fork boundary is the smallest deterministic correction point for this workstream

Exact released fork subject: `elmakus/codex-chatgpt-web@3a6d1d28c28dbe1be885077ae53fe4bba62b9673` (v5.0.15).

`src/native-passthrough.ts` already:
- decodes normal Responses bodies;
- identifies the validated request model;
- applies the Muse-only Gmail namespace omission;
- rewrites the body only when a bounded Muse-specific transformation is needed;
- clears stale `content-encoding` when it rewrites;
- passes the model hint to `src/native-network.ts`, which alone selects Muse versus ordinary native upstream.

Its focused regression tests already prove Muse-only body rewriting, preservation of non-Gmail tools, compressed-body handling, and ordinary-native byte preservation.

The smallest robust correction is therefore to extend that same Muse-only decoded-body normalization so that, for `muse-*` Responses requests, tool entries with `type: "web_search"` keep the tool and every other property but omit only `search_content_types`. Ordinary native and browser-backed paths remain untouched. This is narrower than changing CLIProxyAPI and directly addresses the exact body that failed in production.

An alternative catalog-only fix (`web_search_tool_type: "text"`) matches upstream Codex's preferred provider capability model, but v5.0.15's generated OpenAI-compatible Muse row is already conservative and the real production client nevertheless emitted the failing field. Request-bound normalization is therefore the deterministic correction for the currently shipped client/fork combination; an explicit catalog hint may be added only if later evidence proves it necessary, not as a substitute for the proven request fix.

### 5. Existing accepted Definition remains sufficient

`requirements/MUSE_NATIVE_UPSTREAM.md` R2 already states that every non-Gmail tool entry must remain available to Muse unless independently unsupported by verified evidence. The differential probe proves only one optional property is unsupported while the `web_search` tool remains supported.

The correction does not add a new tool-level capability reduction, does not move routing/filtering into Workstation, and does not require a CLIProxyAPI production mutation. The accepted product/system intent therefore remains valid. What changed is execution strategy beyond approved plan R7, whose T13 Card explicitly excluded additional provider/tool compatibility exceptions.

### 6. Rollback cache state was transient and self-reconciled

Immediately after rollback, `codex debug models` briefly surfaced the five Muse rows from the client's pre-rollback `models_cache.json`. The cache timestamp predated the rollback recreate. On subsequent normal refresh the cache contained only ordinary native + `chatgpt-web/*`; `codex debug models` likewise showed `gpt-5.6-sol` and the three `chatgpt-web/*` rows with no `muse-*` rows.

No manual cache deletion is required. Runtime Muse endpoint readback remains empty, the exact same promoted image is healthy, and route status remains error-free.

## Alternatives considered

1. **Disable web search for Muse** — rejected by evidence: the tool succeeds when only `search_content_types` is absent and would violate the requirement to preserve non-Gmail tools absent independent evidence of full-tool incompatibility.
2. **Patch CLIProxyAPI/Meta executor** — technically possible but exceeds approved R7 strategy, mutates separate production infrastructure, and is unnecessary because the fork already owns Muse-specific request normalization.
3. **Catalog-only `web_search_tool_type: text`** — conceptually aligned with OpenAI provider normalization, but not sufficient as the sole correction for the exact currently observed production request unless independently proven against the shipped Codex client.
4. **Muse-only request-field normalization in `codex-chatgpt-web`** — selected evidence-supported implementation strategy: smallest existing boundary, preserves the tool, isolates Muse, leaves ordinary native/browser paths unchanged, and composes with the existing Gmail filter.

## Research conclusion

The blocker is resolved at the evidence/classification level: Meta Muse rejects only `search_content_types` on the current `web_search` request shape, while the same request without that property succeeds. Existing Project Definition remains valid; approved plan R7 is no longer sufficient because it did not authorize/plan this second compatibility normalization and M01-T13 explicitly excluded it.

Return to `execution_resolution` for classification. The evidence supports **Strategic Planning** as the final owner: revise the execution strategy to add a bounded fork correction, independent review/release, Workstation D25 consumption, then repeat M01-T13 activation/acceptance from the healthy rollback baseline.
