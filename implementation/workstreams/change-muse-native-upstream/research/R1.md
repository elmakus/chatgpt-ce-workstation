## Findings

### Exact runtime failure mechanism

A normal current Codex request was captured through an isolated temporary loopback endpoint using a per-invocation `openai_base_url` override. Production routing was not changed. The request body is zstd-compressed and contained 33 tool entries.

Controls against the real local `codex-chatgpt-web` -> CLIProxyAPI Muse route proved:

- the same request with no tools succeeds;
- the complete normal tool set fails with HTTP 400 / `Recursive JSON schemas are not currently supported`;
- exactly one top-level tool bundle reproduces the failure by itself: `mcp__codex_apps__gmail`.

Within that Gmail namespace, four nested tools independently reproduce the same rejection:

- `_create_draft`
- `_forward_emails`
- `_send_email`
- `_update_draft`

All four carry the recursive definition `#/$defs/GmailMessagePartRequest`. The definition contains `parts[].$ref -> #/$defs/GmailMessagePartRequest`, so a message part can recursively contain message parts. A non-recursive Gmail control tool (`_apply_labels_to_emails`) succeeds through the same Muse route.

Therefore the backend error is not a generic Muse routing/auth/catalog failure. It is a deterministic provider request-schema incompatibility triggered by a real recursive Gmail tool schema in a normal Codex turn.

### Component ownership

Accepted D29 remains coherent:

- Workstation owns only reproducible endpoint/credential lifecycle.
- `codex-chatgpt-web` owns parallel model routing/catalog filtering and already routes the request to the correct Muse upstream.
- CLIProxyAPI owns the Meta/Muse provider executor and provider-specific request compatibility before forwarding to `api.meta.ai/v1/responses`.

Upstream CLIProxyAPI source at `router-for-me/CLIProxyAPI@a5ab69521f7b4e0f244836d0419da8fcd89408ea` confirms:

- `internal/runtime/executor/meta_executor_execute.go` / `meta_executor_stream.go` translate and forward Meta requests but do not apply a recursive-tool-schema compatibility transform.
- `internal/runtime/executor/helps/codex_tool_schema.go` already contains provider/proxy-side Codex tool-schema normalization and recursively traverses namespace tools, but currently normalizes only bounded known incompatibilities such as constant unions and unsupported regex patterns.
- `NormalizeCodexToolSchemas` is applied on Codex executor paths, not on the Meta executor path.
- Existing CLIProxyAPI issue history includes tool-schema normalization fixes, supporting the same provider-compatibility ownership boundary.

Adding a Muse-only strip/flatten operation in Workstation would violate D29. Adding it blindly in `codex-chatgpt-web` would also be unsafe because removing or truncating a recursive schema changes the semantics of Gmail MIME/message-part input.

### Existing Codex configuration

Current Codex supports plugin enable/disable controls and session-level disabled plugin IDs, but no evidence was found for an automatic model-specific mechanism that transparently removes only the incompatible Gmail actions for Muse while preserving normal plugin/tool availability.

Globally or manually disabling Gmail/apps is therefore a workaround with capability loss, not a transparent acceptance-grade fix.

### Strategy classification

The accepted requirements and D29 do not need to change. The new evidence changes the remaining execution strategy:

1. keep Muse production activation rolled back while normal Codex Muse turns are incompatible;
2. correct or prove a semantics-preserving compatibility behavior at the CLIProxyAPI Meta-provider boundary;
3. only after that correction is immutable/deployed, rerun normal Codex Muse smoke with the recursive Gmail namespace still present;
4. if Meta cannot accept any semantics-preserving representation of the recursive schema, escalate to Project Definition before accepting capability loss such as omitting Gmail tools for Muse.

This is a **Strategic Planning** correction, not bounded T07 execution.
