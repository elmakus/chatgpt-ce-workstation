## Known incident evidence

- Incident and bounded recovery are summarized in `implementation/workstreams/issue-codex-interrupt-hook-drift/INTAKE.md`.
- The persisted hook retained the exact journal-owned command, state key, trusted hash, type, and timeout; the only semantic drift inside the managed block was `enabled = false`.
- The retained launcher log records the first mismatch at `2026-09-19T02:13:39.879Z` (`2026-09-19 04:13:39` Europe/Zurich), before the v5.0.14 update.
- Both retained v5.0.13 and v5.0.14 refused to overwrite the changed hook.
- Removing only `enabled = false` restored a journal-exact managed block; the next same-image launcher restart completed runtime migration/start and restored ordinary Sol routing.

## Verified upstream behavior

The upstream OpenAI Codex source already had the relevant behavior by commit `cbfd999db78cb088d2bd89b52051efe6f44555a4` (2026-08-25, "Add hooks for interrupted turns"), so it predates the 2026-09-19 incident.

1. `codex-rs/tui/src/bottom_pane/hooks_browser_view.rs`
   - `toggle_selected_hook` flips `hook.enabled` and emits `AppEvent::SetHookEnabled { key, enabled }`.
   - The hook browser explicitly says: "Turn hooks on or off. Your changes are saved automatically."
   - The toggle is rejected only for `hook.is_managed` or hooks still awaiting trust review.

2. `codex-rs/tui/src/app/background_requests.rs`
   - `write_hook_enabled` persists the toggle with `ConfigBatchWrite`.
   - It writes an Upsert to `hooks.state` with exactly:
     `{ <hook-key>: { "enabled": <bool> } }`.
   - Because this is an Upsert into the existing state table, an existing `trusted_hash` is preserved while `enabled = false` is added. This exactly matches the incident's forensic shape.

3. `codex-rs/config/src/hook_config.rs`
   - `HookStateToml` contains independent optional fields `enabled: Option<bool>` and `trusted_hash: Option<String>`.

4. `codex-rs/hooks/src/engine/discovery.rs`
   - User-config hooks are classified as `(HookSource::User, false)`, i.e. not managed.
   - `hook_enabled` disables an unmanaged hook when its state has `enabled = false`.
   - The codex-chatgpt-web hook is installed in the user `~/.codex/config.toml`; the textual `# Managed by codex-chatgpt-web` marker is not a Codex managed-layer signal. Therefore Codex legitimately exposes this hook as toggleable even though codex-chatgpt-web treats the fragment as journal-owned.

Current upstream `main` retains the same behavior.

## Writer attribution

### Verified

The persisted `enabled = false` is valid, intentional Codex hook-state semantics, not a malformed migration artifact. Native Codex contains a direct writer whose output shape matches the incident exactly.

The launcher/integration path is not the writer of this state. In `elmakus/codex-chatgpt-web`, the interrupt-hook verifier intentionally accepts only the exact journal-owned hook plus the known native `enabled = true` normalization. It rejects `enabled = false` with `Codex interrupt lifecycle hook changed after setup; refusing to overwrite it`. Tests explicitly assert that `enabled = false` remains rejected.

### Not recoverable from retained evidence

The retained logs do not record the successful pre-failure `config/batchWrite` request that introduced the field, and retained Codex session JSONL contains no user `/hooks` message proving the exact gesture. Therefore the precise initiating actor cannot be proven as a specific Enter/Space press versus another Codex client invoking the same config-write API.

The highest-confidence producer class is nevertheless the native Codex hook-enable/disable path, because:
- its persisted representation is byte-for-semantic-field identical to the observed drift;
- it existed before the incident;
- it preserves the existing trusted hash exactly as observed;
- no launcher/migration path found writes `enabled = false` onto this hook.

## Failure chain

1. codex-chatgpt-web installs a journal-owned Interrupt hook in the user config and records its trusted hash/state key.
2. Codex sees that hook as an unmanaged user hook.
3. A native hook-enable/disable write persists `enabled = false` into the same state entry while preserving `trusted_hash`.
4. The hook stops executing, but the broader route can remain installed/active enough that the problem is latent.
5. On a later launcher/runtime start or migration, codex-chatgpt-web performs strict ownership verification.
6. The verifier correctly treats `enabled = false` as drift and refuses to overwrite it.
7. Runtime startup/fail-safe route restoration both hit the same invariant, so the local Responses listener never returns while the route still points traffic at it.
8. This produces the observed full routing outage for both ordinary Sol and chatgpt-web models.

The strict verifier is therefore not the root cause; it is the point where an unresolved compatibility conflict becomes a fail-closed outage.

## Smallest safe compatibility fix

The compatibility rule should distinguish **native enablement-state drift** from **identity/definition drift**.

Recommended bounded behavior:

- Status/verification must continue to treat `enabled = false` as unhealthy/inconsistent; a disabled lifecycle hook must never be reported as a healthy active route.
- During explicit setup/upgrade/recovery of the route, codex-chatgpt-web may self-heal `enabled = false` **only when** the journal proves the same managed hook identity and every other owned field still matches exactly: managed markers/location, command, hook event/type, timeout, journal state key, and trusted hash.
- That repair should remove the native disable override or restore enabled state, then re-verify the exact journal-owned fragment before continuing.
- Any other change remains fail-closed and must still produce the existing "changed after setup" refusal.
- Tests should cover the exact incident shape and prove that command/hash/type/timeout/state-key/structural mutations are still rejected.

This preserves the safety purpose of strict ownership while recognizing a Codex-owned state field that Codex intentionally allows users/clients to mutate.

## Alternatives considered

- Treat `enabled = false` as healthy: rejected; the lifecycle invariant would be false while the route is reported active.
- Blindly overwrite any changed managed block: rejected; this weakens ownership/tamper protection.
- Move the hook into a Codex managed config layer so the UI cannot toggle it: not the smallest compatibility fix and materially changes deployment/ownership boundaries.
- Patch upstream Codex to special-case codex-chatgpt-web markers: broader coupling than required for the current issue.

## Research conclusion

Root cause is an ownership-model mismatch: codex-chatgpt-web regards the Interrupt hook fragment as strictly journal-owned, while Codex regards a hook sourced from user `config.toml` as user-toggleable and persistently records that toggle in the same `hooks.state` entry.

The exact initiating gesture is not provable from retained logs, but the writer class, intentional Codex semantics, failure chain, and bounded compatibility rule are established strongly enough for Project Definition. No remaining research uncertainty blocks definition or planning.
